# E7.3 Normal / Test A / Test B on one board, one ST reference chain (2026-10-05)

Chain: STiRoT (HDPL1, ST system flash) -> OEMuRoT 2.0.0 (HDPL2, ST OEMiROT_Boot with OEMUROT_ENABLE,
DEV_MODE) -> full-secure app 1.0.0 (HDPL3). Open, TZEN 0xB4, BOOT_UBE 0xC3, SECBOOT_LOCK 0xB4.
Every tamper is one bit at offset 0x1400 of the image body (H0 record). Per-test records:
-m7-e71-ct-bl-*.txt, -m7-e72-ct-app-*.txt. Verdicts are the user's.

  OEMuRoT 2.0.0 -> counter 0 : ok -> hash ref OK -> Jumping to the first image slot -> User App #A.

  Not restored byte for byte: the app primary and the OEMuRoT execution area now carry the

## What the table shows

- Each trust boundary is held by the layer above it. OEMuRoT refused every modified app image,
  installed or offered as an update. STiRoT refused every modified OEMuRoT image, installed or
  offered as an update.
- The two refusal layers look the same from outside (both land in the System Bootloader when no
  valid image is left) and differ in the log: an OEMuRoT refusal prints its reason; a STiRoT
  refusal prints nothing, because OEMuRoT never runs.
- Integrity and authenticity failures are separate paths in OEMuRoT: a bad body stops at the hash
  check with no signature line (CT-APP-HASH); a consistent hash with a foreign signature stops at
  "signature KO" (CT-APP-SIG). This closes the M3 log question.
- The controls installed the same images through the same paths, so each refusal is attributable
  to the modification, not to the path, the version or the counter. Both download controls reused
  the installed version: OEMuRoT and STiRoT both accept an equal security counter.

## Side results

- Writing secure flash needs a core halted before the chain configures its protections (mode=UR,
  SW1=0); Hotplug with the app running failed and left the app slot half written (F-05).
- With SW1=0 the chain is bypassed and OEMuRoT runs from SECBOOTADD without STiRoT; it then stops
  at "read: Wrong OBK HDPL2 cfg" because its HDPL2 OBK data is not readable at that HDPL.
- While the app runs, both download slots read as zero over SWD; their real state was read under
  reset.
- Security finding: the ST MCUboot fork prints the decrypted image AES key at INFO
  (encrypted.c:703), which DEV_MODE puts on the VCP. Masked in the M7 logs; an M8 requirement.

## Limits

- OEMuRoT ran in DEV_MODE (D-07). The release behaviour (logs off, reset instead of while(1) on
  Error_Handler paths) was not tested.
- Product state Open: BOOT0 bypasses STiRoT. Closed-state behaviour is M11.
- STiRoT is closed ROM code; its refusals are shown by state (no OEMuRoT run, System Bootloader,
  unchanged or tampered execution area), not by a log.
