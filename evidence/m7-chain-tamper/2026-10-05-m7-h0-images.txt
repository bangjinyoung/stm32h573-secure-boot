# M7 H0: tamper images for the CT tests (2026-10-05, host only, no board access)

Source build: build/stirot_oemurot (scripts/build_stirot_oemurot.sh, OEMuRoT 2.0.0, app 1.0.0,
CubeH5 e5c73ea1, E6.1). The generated binaries stay out of git (.workspace/tmp/m7/); this record
holds what is needed to regenerate and check them. CT ids are reused unchanged by M8.5.

Every modification is bit 0 of the byte at offset 0x1400 (header 0x400 + 0x1000), inside the image
body, not in the header or the TLVs, as in M5. Download images are AES-CTR encrypted, so the flip
lands on the same plaintext bit after decryption.

ECDSA signing is randomized, so a regenerated b3 has another sha256. It is reproduced by its
properties, checked with `mcuboot_image.py check <img> <trusted pub> <M2 key>`:

| image | hash TLV | keyhash = trusted key | signature, trusted key | signature, M2 key |
|---|---|---|---|---|
| source app 1.0.0 | MATCH | MATCH | VALID | INVALID |
| b2 | MISMATCH | MATCH | INVALID | INVALID |
| b3 | MATCH | MATCH | INVALID | VALID |

Trusted key for the app: OEMuRoT_Authentication_S.pem (ROT_Provisioning/STiROT_OEMuROT/Keys in the
build copy). b3's image hash 32ab83f1... differs from the stored hash reference 1aa954b5... (app
1.0.0), so OEMuRoT cannot take the hash-ref shortcut.

## Expected validation path (prediction from code, the board decides)

Why b3 has to look like this (ST MCUboot fork v1.7.2.40, bootutil/src/image_validate.c):
- The SHA256 TLV is compared first; a mismatch leaves without a log line (443-459).
- A keyhash that names no trusted key leaves before any signature log (463-482).
- A body equal to the stored hash reference skips the signature (517-559).

| CT id | expected OEMuRoT log | expected SWD |
|---|---|---|
| CT-APP-HASH | counter 0 : ok -> Image in the primary slot is not valid! -> Unable to find bootable image; no "signature" or "hash ref" line | PC 0x0C00D7A4 (Error_Handler, .BL2_Error_Code) |
| CT-APP-SIG | verify sig key id 0 -> checking public key 47 5b -> verifying signature hlen 20 -> signature KO -> not valid -> Unable to find bootable image | PC 0x0C00D7A4 |
| CT-APP-DL-CTRL | Image upgrade secondary slot -> primary slot -> hash ref OK -> app | download slot erased |
| CT-APP-DL | Image in the secondary slot is not valid! -> hash ref OK -> app 1.0.0 | primary readback = source |
| CT-BL-EXEC | no OEMuRoT banner | VTOR 0x0BF97000 / PC in System Bootloader, DSCSR CDS=0 |
| CT-BL-DL-CTRL | Starting bootloader OEMuROT 2.0.0 again | execution area readback = rot_init_sign.bin |
