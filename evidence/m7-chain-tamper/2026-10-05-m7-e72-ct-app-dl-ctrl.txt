# E7.2 CT-APP-DL-CTRL: valid encrypted app 1.0.0 in the download slot, OEMuRoT installs it (2026-10-05)

Control for CT-APP-DL. Image rot_tz_s_app_enc_sign.bin (objcopy of rot_tz_s_app_enc_sign.hex,
sha256 b623fd75...), app 1.0.0, AES-CTR encrypted body, trailer boot magic at 0x7ff0. Same version as
the installed app, so the security counter is not consumed (image_validate.c:625 rejects only <).
Its header (first 0x400 bytes) equals the init image's byte for byte.

## Readback after the boot (13:41, Hotplug, read-only), -m7-w5-postboot-check.log

- Primary 0x0C018000: header and body equal rot_tz_s_app_init_sign.bin; 180 bytes differ in
  0x5b7f-0x7fe0, which are the unprotected TLVs (signature and ENC TLV of the download image, not of
  the init image) and the trailer (0x7fd0 01 -> ff). The primary now holds the decrypted download
  image, so the content came from the download slot. The hash covers header, body and protected
  TLVs only, which are unchanged, so the stored hash reference still matched (hash ref OK).
- Download slot 0x08020000 read 0x00 in all 32768 bytes. 0x00 is not the erased value (0xFF), and the
  same slot read correctly before the boot with OEMuRoT halted. Inferred: read-as-zero while the app
  runs, not the slot content. The erase after the copy (loader.c:2181-2192) is to be checked under
  reset before W6 writes the slot.

## Security finding: the decrypted image key is printed to the UART

The ST MCUboot fork prints the unwrapped AES-128 image key, 8 bytes per line, at INFO level
(bootutil/src/encrypted.c:703, also :551 for RSA). OEMuRoT DEV_MODE sets BOOT_LOG_LEVEL_INFO
(low_level_security.c:27-31), so every encrypted install leaks the key of that image on the VCP.
The four lines are masked in 2026-10-05-m7-vcp.log and in the captures; the raw bytes were not
kept. Release builds set BOOT_LOG_LEVEL_OFF. For M8: the custom MCUboot must not log key material.
